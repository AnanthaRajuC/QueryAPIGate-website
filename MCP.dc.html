QueryAPIGate for AI agents · MCP server

Give your AI agents your data, and keep the keys.

QueryAPIGate is a governed MCP server for your databases. Your saved SQL queries become tools any MCP agent can call: Claude, your own agent, an IDE. The server, not the prompt, decides what each agent may see, change and spend. Masking, human approval for writes, quotas and a tamper-evident audit trail are built in, not bolted on.

Self-hosted. Your data never leaves your infrastructure. Every database it reaches, it reaches with the credentials you gave it, never the agent's.

Saved queries as tools

A read tool returns rows the caller may see. A write tool returns a link; a person approves it, then it runs once, inside a transaction, and lands in the audit log.

The problem

Security said no. Here's how they say yes.

Everyone wants to "connect the AI to the database". The first design that comes to mind, an MCP server holding a database login and offering the agent execute_sql, is the one security teams rightly block:

  • ✕An agent is an untrusted user that is very fast and very easy to fool. One poisoned document in its context and it will ask for anything.
  • ✕"Please don't read the salaries table" in a system prompt is a request, not a control.
  • ✕Nobody can answer the questions that matter afterwards: which agent read what, for whom, and who allowed it?

QueryAPIGate moves every one of those rules out of the prompt and into the server. The agent can be tricked; the gateway can't be talked out of its grants.

What agents get, and what they never get

Eight controls, in the server

Each is a grant, a setting or a policy you configure once; none of them lives in a prompt.

01

Curated tools, not a database login

Write the SQL once. Publish it. It's a tool, with a typed input schema generated from its declared parameters: the agent can't send a value the parameter's rules refuse, and every value is a bound parameter, never text spliced into SQL.

When an agent does need to explore, two ad-hoc tools, list_tables and execute_sql, are available only to a key granted a connection, limited to the tables you list, and always read-only: over MCP, execute_sql never writes, whatever the same key could do over REST.

Ad-hoc tools, limited to the tables you choose →
02

Least privilege, per agent

Each agent gets its own key, or signs in as the person it acts for, with exactly the queries, collections, connections and tables it needs. tools/list shows an agent only what it may call; calling anything else by name is refused. The same grant applies over REST: an agent can never reach more than an application with the same key.

03

Masking that follows the data, not the column name

Hash, mask or drop a column for a caller (email, national_id, salary) and QueryAPIGate traces it through the SQL: renamed (SELECT email AS contact), joined, inside an expression, through a view. A query whose columns it can't trace is refused before it runs, not answered with the value unmasked. The agent is told which columns it gets masked, so it doesn't guess.

04

Agents that write, only when a person says yes

Mark a saved query for agents and its first call writes nothing: it returns a link. A person sees the agent, the SQL, the exact arguments and the row ceiling, and approves or rejects it in the Console. The agent then runs exactly that write, once, before the approval expires, inside a transaction that rolls back if it changes more rows than allowed. The credential that asked can never approve its own write.

Let an agent write, with a person approving each write →
05

Agents sign in as the person they act for

A hosted AI client doesn't hold a shared key: it follows MCP's OAuth 2.1 authorization, and your identity provider, any OpenID Connect provider (tested with Keycloak), signs the person in. The agent then acts under that person's role and masking rules, and a query that binds a parameter to the token (from_claim) returns only that person's rows. QueryAPIGate checks tokens and issues none; it never sees a password, and a token issued for REST is never accepted for MCP, or the reverse.

Let AI clients sign in through your identity provider →
06

Limits that hold when an agent loops

Per-agent rate limits, daily or monthly quotas on calls and rows, a cap on concurrent queries, a query time limit, and a row cap on every tool result (QUERYAPIGATE_MCP_MAX_ROWS, 200 by default, sized for a context window). Shared across every instance through Redis, and across REST and MCP together.

07

Everything on the record

Every tool call lands in run history with "transport": "mcp": which agent, which query, which arguments' names, how many rows. Every change to who may do what is in an audit log with a hash chain, so an edited or deleted entry is detectable, and it streams to your SIEM. The Agents screen shows each agent's use; an alert fires when an agent suddenly reads far more than its usual.

Tell agents what your data means, and see what they did →
08

Agents that understand your data

Most wrong answers aren't the model's fault: nobody told it that revenue is SUM(payment.amount), not rental.amount. QueryAPIGate imports your database's own table and column comments, lets you write the rest (which joins to use, what each metric means) and gives it to the agent with every list_tables and as an MCP resource per connection. Results come back as structuredContent with an outputSchema, so your code reads rows, not prose.

Your security review, answered

What your security team asks

Each answer is a control on the server, with a guide that shows it working.

Your security team asksQueryAPIGate
Can the agent run arbitrary SQL?Only if you grant it execute_sql on named connections and tables, and then read-only, always.
Can it write?Only through queries you marked for agents, each write approved by a person, capped in rows.
Can it see personal data?Not the columns you mask: traced through the SQL, refused when it can't be traced.
What if it's prompt-injected?It can ask for anything; it gets only what its grant allows. The boundary is the server, not the model.
Whose identity does it act under?Its own key, or the signed-in person's, with their role and row-level from_claim binding.
Can it run up costs or load?Rate limits, quotas on calls and rows, concurrency caps, time limits and a result row cap.
Can we prove what it did?Run history for every call; a hash-chained audit log, streamed to your SIEM.
Where does our data go?Nowhere: self-hosted, on your infrastructure, reaching your databases with your credentials.

Ten minutes

Ten minutes to your first governed tool

Save a query in the Console's API Designer and publish it: it's a tool. Create a key for your agent with only the queries it needs. Point any MCP client that speaks Streamable HTTP at http://<host>:5001/mcp with the key as the X-API-Key header, or turn on OAuth and let it sign in.

Honest limits
  • Masking isn't available on MongoDB, H2 or generic JDBC connections; a caller with mask rules is refused there.
  • Approved writes run on PostgreSQL, MySQL (transactional tables), SQLite and DuckDB; one INSERT, UPDATE or DELETE per tool.
  • OAuth needs JWT access tokens signed with an asymmetric key; QueryAPIGate checks tokens and doesn't issue them.
FAQ

Questions people ask before they connect an agent

Does the AI model ever see database credentials?

No. Agents authenticate to QueryAPIGate; QueryAPIGate reaches your databases with each connection's own credentials, stored encrypted, and never passes a token or password on.

Which AI clients work?

Any MCP client that speaks Streamable HTTP and can send a header (for an API key) or follow MCP's OAuth (for sign-in): agent frameworks, IDE assistants and hosted assistants' connectors.

Can an agent read data it shouldn't by rephrasing its question?

Its question doesn't matter; its grant does. It can call only the tools its key or role allows; execute_sql, if granted at all, is read-only and limited to the tables you named; masked columns stay masked however the SQL is written, or the query is refused.

Do I have to rewrite anything for REST?

No, it's the same query. The tool you publish for agents is also GET /q/<name>, with an OpenAPI description, and can be exported to Parquet on S3 on a schedule.

What happens when an agent loops?

Its rate limit refuses it, its quota stops it for the day or month, and its concurrency cap keeps it from tying up your database, each a clear, machine-readable error it can act on.

Your agents can be fast, helpful and easy to fool. Your data layer shouldn't be.
