QueryAPIGate for AI agents · MCP server

Give your AI agents your data, and keep the keys.

QueryAPIGate is a governed MCP server for your databases. Your saved SQL queries become tools any MCP agent can call: Claude, your own agent, an IDE. The server, not the prompt, decides what each agent may see, change and spend. Masking, human approval for writes, quotas and a tamper-evident audit trail are built in, not bolted on.

Self-hosted. Your data never leaves your infrastructure. Every database it reaches, it reaches with the credentials you gave it, never the agent's.

01 · What's exposed

Saved queries become tools. The key's grant decides which.

Read-only saved queries (SELECT, WITH, SHOW, DESCRIBE, EXPLAIN and any Mongo find(), the same classification the REST write guard uses) become MCP tools. A query that writes becomes one only when its author marked it for agents, for a key whose grant allows the write, and a person approves each write first. Ad-hoc SQL never writes over MCP.

Listing is the key's catalogue

tools/list honours exactly the per-key scoping GET /catalog does: connections, queries and collections grants. An agent's key never sees or calls more than the identical REST key could.

Input schemas from the query itself

A tool's inputSchema is generated from the saved query's own declared parameters, the same JSON Schema translation /openapi.json already uses.

One code path with REST

tools/call runs the query through the exact path GET /q/<name> does: the same grant check, parameter validation, cache_ttl caching, run history and audit trail. A run over MCP shows in the Console's History and the Home tab's live feed like a REST call.

02 · Structured results (outputSchema)

Rows your code reads, not prose it parses

Every tool, a saved query, list_tables or execute_sql, declares an outputSchema, and every successful call returns a matching structuredContent alongside the usual text content. A row-returning tool always answers {"rows": [...], "truncated": <bool>}; list_tables answers {"tables": [...], "truncated": <bool>}.

A generic envelope, on purpose

A saved query's result columns are only known once it runs, not from its stored definition, so declaring per-column types would need a new admin-authored field. The envelope is the same for every tool.

The text block is a copy

The text content is a serialised copy of the same object, kept for clients that do not read structuredContent. The first text block is always pure JSON.

Breaking, if you integrated earlier

A row-returning tool's text used to be a bare JSON array with a "(truncated to N rows)" suffix. It is now always the wrapped object: read structuredContent directly, or parse the text as the new shape.

Threat model →

list_tables

{"connection_name", "database"} (database is admin-key only, as over REST). The same shape GET /connections/<name>/schema returns: every table, view or Mongo collection with its columns, types, nullability and keys where the dialect has them.

describe_table

{"connection_name", "table", "database"}. One table's columns, types and keys, masking-aware: a masked or dropped column is flagged, never shown as readable. A table the key cannot reach answers exactly as a missing one (table_not_found), so it cannot probe outside allowed_tables.

execute_sql

{"connection_name", "sql", "params", "page_size", "database"}. A single read-only statement, always read-only over MCP whatever the key's allow_writes grant; allowed_tables still applies. Results are capped to QUERYAPIGATE_MCP_MAX_ROWS like a saved-query call.

No separate path to drift

Both reuse the permission checks and execution code the REST API already has. An execute_sql call is recorded in run history like a POST /execute_sql one, with "transport": "mcp".

04 · Running it

Ten minutes to your first governed tool

Save a query in the Console's API Designer and publish it: it's a tool. Create a key for your agent with only the queries it needs. Point any MCP client that speaks Streamable HTTP at http://<host>:5001/mcp with the key as the X-API-Key header, or turn on OAuth and let it sign in. The Console's own MCP screen shows the workspace's live tool list, a reachability check and the connect snippet.

Its own port

QUERYAPIGATE_MCP_PORT, default 5001, separate from queryapigate serve, so both run side by side against the same QUERYAPIGATE_HOME. The endpoint is http://<host>:<port>/mcp, speaking Streamable HTTP; /metrics and /health on the same port report on this process.

A separate process, not a mode

MCP's HTTP transport is ASGI-native, while the REST API is WSGI (Flask on gunicorn). So queryapigate mcp is its own server, started with the same variables.

The same code, by direct import

What matters for correctness, reusing the project's own connection-grant checks, caching and audit logging, happens by direct Python import, not an HTTP round-trip back to the REST API, whichever process each server runs in.

import asyncio
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

KEY = "your-api-key"

async def main():
    async with streamablehttp_client("http://127.0.0.1:5001/mcp", headers={"X-API-Key": KEY}) as (r, w, _):
        async with ClientSession(r, w) as session:
            await session.initialize()

            tools = await session.list_tools()
            print([t.name for t in tools.tools])

            result = await session.call_tool("example_top_films", {"top_n": 3})
            print(result.structuredContent)

asyncio.run(main())

The same credentials as REST

An X-API-Key header checked against the same server key and scoped keys, or, with signed-in users on, an Authorization: Bearer token, so an agent acting for a user gets that user's role and from_claim row filters. A call carrying an API key is judged on that key alone; a wrong key never falls back to the token.

In a header, never the URL

Send either as a request header, the way any HTTP-capable MCP client configuration allows. A credential in a URL parameter would leak into logs. An unset server key means open access, as over REST.

Refused before the session

Every request to /mcp is checked before the MCP session sees it: a missing or wrong credential is an HTTP 401 with WWW-Authenticate, a refused one a 403, and the rate limit a 429, each with the {"error", "code", "request_id"} body REST uses.

06 · Sign-in for AI clients (OAuth)

Agents sign in as the person they act for

A hosted AI client, a connector in an assistant, takes no API key: it follows the MCP specification's authorization, OAuth 2.1. The MCP server is the resource server, checking tokens; your identity provider (Keycloak, Okta, Auth0, Entra ID) issues them, signs the user in and registers the client. QueryAPIGate never sees a password. Stable since 0.30, under the compatibility promise.

Discovery

GET /.well-known/oauth-protected-resource (and …/mcp) is the server's Protected Resource Metadata (RFC 9728): its URL, authorization_servers, scopes_supported. A 401 points at it in WWW-Authenticate, which is how a client knows where to sign the user in.

What a token must be

Signed by the provider's published keys with the key's own algorithm; iss the provider; aud the MCP server's URL; not expired; carrying the scope as scope or scp. Anything else is 401 invalid_token. Valid without the scope: 403 insufficient_scope. A user with no role here: 403 forbidden.

Tokens are kept apart

A token issued for the REST API is not accepted on /mcp, and REST refuses a token naming the MCP server, so one leaked from either cannot be replayed against the other. API keys still work for SDKs and scripts. No token is ever passed on: databases are reached with the connection's own credentials.

What the agent may do

Its role's: connections, saved queries, allowed_tables, rate limit and masking rules. from_claim parameters bind to the token's claims, so an agent acting for a person sees only that person's rows. Its runs are in history as jwt:<sub> with "transport": "mcp", or mcp:<sub> when REST trusts another issuer.

Registering the client

Between the client and your provider: Client ID Metadata Documents or Dynamic Client Registration where supported, or an administrator registering it by hand. QueryAPIGate plays no part and issues no tokens of its own.

Limits

QueryAPIGate checks tokens and issues none, so registering clients and revoking tokens are the provider's. A token must be a JWT signed with an asymmetric key; an opaque one is refused. A token is valid until it expires.

Approved writes →

"agent_writes": "approval"

The first call writes nothing: it answers approval_required with a request id and an approve_at link. An administrator with writes.approve approves or rejects it. The agent calls again with the same arguments and approval: "wr_…": it runs if approved, for this caller, with exactly these arguments, before it expires (15 minutes by default), and once.

"agent_writes": "insert"

A single INSERT runs at once, with an optional idempotency_key so a retry within a day returns the first call's result instead of inserting again.

max_affected_rows

Default 1. The write runs in a transaction, rolled back when it changed more rows (too_many_rows_affected, nothing changed). On MySQL keep these queries on InnoDB tables; MyISAM cannot roll back.

What comes back, and what is kept

RETURNING is masked like any read. Every request is kept 30 days (GET /api/v1/write-requests); the run is in history with request and approved_by; approvals and rejections are in the audit log. QUERYAPIGATE_CONSOLE_URL makes approve_at a full link.

In the Console

Observability → Approvals, with a count of waiting writes in the sidebar. The link an agent is given opens its request there: the agent, the SQL, the exact arguments, the row ceiling, when it expires, with Approve and Reject. The writes_awaiting_approval alert says when writes are waiting; the Agents screen counts each agent's requests by how they ended.

Four eyes

A write is never approved by the credential that asked for it (own_write), so give agents their own keys. An agent with 100 writes waiting is refused more (too_many_pending_writes).

09 · Governance: the same rules as REST

There is no "AI security" to configure separately from "API security"

Every tool call passes through the same checks a REST request does, in the same order, by calling the same code. That matters because an agent is an untrusted user that is very fast and very easy to fool: one poisoned document in its context and it will ask for anything, and "please don't read the salaries table" in a system prompt is a request, not a control. QueryAPIGate moves every rule into the server, where the gateway cannot be talked out of its grants.

Where data goes →

Four checks, in order

1. QUERYAPIGATE_RATE_LIMIT per client address, before authentication, so guessing keys is throttled too. 2. Authentication. 3. The caller's own rate_limit grant. 4. Grants: connections, queries, collections, allowed_tables, IP allow-lists, then the tool itself.

Refusals an agent can branch on

Past authentication, a refused call is a tool error (isError: true) whose text says why and whose structuredContent carries the same {"error", "code"} a REST error body does: rate_limited (with retry_after), unauthorized, table_not_allowed, read_only, param_invalid and the rest.

Told apart in metrics

Every call is counted in /metrics with method MCP and endpoint mcp.saved_query, mcp.execute_sql or mcp.list_tables. Saved-query and ad-hoc runs land in run history and live events with "transport": "mcp".

Limits shared through Redis

With QUERYAPIGATE_REDIS_URL set for both processes, a key's 100/minute is 100 calls over REST and MCP together. Without it each process counts on its own, as two instances would.

Metrics per process

queryapigate mcp serves its own GET /metrics and GET /health on its port, open or behind QUERYAPIGATE_METRICS_TOKEN as the REST server's. Scrape both.

The CLI is a local operator

queryapigate export reads the store directly with no key, so no grant or rate limit applies: whoever can run it can already read QUERYAPIGATE_HOME. Its runs are still recorded, with key_name cli.

Honest limits
  • Masking isn't available on MongoDB, H2 or generic JDBC connections; a caller with mask rules is refused there.
  • Approved writes run on PostgreSQL, MySQL (transactional tables), SQLite and DuckDB; one INSERT, UPDATE or DELETE per tool.
  • OAuth needs JWT access tokens signed with an asymmetric key; QueryAPIGate checks tokens and doesn't issue them.
  • Semantic search (embed) is experimental and PostgreSQL/pgvector only; it needs an OpenAI-compatible embeddings endpoint you run (OpenAI, Azure, or a local Ollama).
Does the AI model ever see database credentials?

No. Agents authenticate to QueryAPIGate; QueryAPIGate reaches your databases with each connection's own credentials, stored encrypted, and never passes a token or password on.

Which AI clients work?

Any MCP client that speaks Streamable HTTP and can send a header (for an API key) or follow MCP's OAuth (for sign-in): agent frameworks, IDE assistants and hosted assistants' connectors.

Can an agent read data it shouldn't by rephrasing its question?

Its question doesn't matter; its grant does. It can call only the tools its key or role allows; execute_sql, if granted at all, is read-only and limited to the tables you named; masked columns stay masked however the SQL is written, or the query is refused.

Do I have to rewrite anything for REST?

No, it's the same query. The tool you publish for agents is also GET /q/<name>, with an OpenAPI description, and can be exported to Parquet on S3 on a schedule.

What happens when an agent loops?

Its rate limit refuses it, its quota stops it for the day or month, and its concurrency cap keeps it from tying up your database, each a clear, machine-readable error it can act on.
