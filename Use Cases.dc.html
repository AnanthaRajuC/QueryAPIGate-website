01 · Product teams

Data inside your product, for your customers and your staff

For SaaS products

Put analytics in front of your customers, one tenant at a time

Customers want their own numbers inside your product. Building that usually means an analytics backend with tenant isolation you have to get exactly right. Here, each user signs in with the token your app already issues, and the tenant comes from that token, never from the request.

Read the use case →
whojwt:bob@tools.internal doorGET /q/my_open_tickets email from token ✓CORS: tools.internal ✓cache shared via Redis ✓ dataPostgreSQL · tickets 02 / 12
For internal tools and dashboards

Back an internal app without a backend team

A frontend needs six queries from three databases. That is six endpoints, three drivers and one more service to keep alive. Or it is six saved queries, one key with JWT sign-in for your app's users, and CORS.

Read the use case →
whokey acme-orders doorPOST /q/acme_submit_order server allows writes ✓this one query only ✓sku, qty typed and bound ✓ dataPostgreSQL · shop 03 / 12
For operational workflows

Let a partner or a form write, through one approved query

Sometimes the job is putting data in: a partner submitting orders, a form filing a request, a support lead correcting a record. Writing is off by default at every level, and you open one query, for one caller, and nothing else.

For a partner or customer

Hand a partner one query, not your schema

A customer wants their orders. The usual answer is a bespoke endpoint, an auth middleware and a quarter of review time. The alternative is a scoped key that can call exactly one saved query, written for their rows.

Read the use case →
whocron 02:00 doorqueryapigate exports run since = last watermark ✓one run at a time ✓locked to the prefix ✓ datas3://acme-inbound/orders/…parquet 05 / 12
For pipelines and partners' buckets

Deliver a daily file, incrementally, to someone else's bucket

Every night a partner needs yesterday's changes as Parquet in their S3 bucket. Writing that job means credentials, retries, a watermark and a place to see when it failed. A saved export is all of those.

Read the use case →
whobrowser · key in header doorGET /events per-key feed ✓every instance, one stream ✓filter by query · kind ✓ datarun history · shared store 06 / 12
For operations screens

A live view of what is being queried, by whom

A wall display or a client that reacts when a query runs. GET /events streams each run as it completes, per key if you want, fanned out across instances by the events server.

03 · Data teams

Access for everyone who needs it, without handing out the database

Self-serve dataFiles as an APILegacy databases
whokey finance-reporting doorGET /catalog → /q/revenue_by_region collection finance only ✓read-only ✓600/hour budget ✓ datarevenue_by_region · cache 300s 07 / 12
For data and analytics leads

Self-serve data for every team, without handing out the database

Ten teams want data from the warehouse. Shared database passwords leak, and routing every request through the data team as a ticket doesn't scale. Publish saved queries in collections instead, give each team a role, and let people find what they can use.

Read the use case →
whoan analyst's key doorsaved query over view events allowed_paths only ✓auto views per prefix ✓grants + masking as usual ✓ datas3://acme-lake/events/*.parquet · DuckDB 08 / 12
For data teams

Turn a bucket of Parquet into a queryable API

The lake has the data; the people who need it have a browser and curl. A DuckDB connection pointed at a prefix makes each file a view, locked to the paths you list, with no copy and no warehouse.

Read the use case →
whokey procurement doorGET /q/open_purchase_orders vendor's driver via JDBC ✓database user read-only ✓masking + audit as usual ✓ dataOracle · erp (jdbc) 09 / 12
For legacy and vendor databasesEXPERIMENTAL

Put a governed API in front of a database you can't change

The core system runs on Oracle, SQL Server or DB2, and nobody wants to touch it. Generic JDBC loads the vendor's own driver, so that data can be served through saved queries with the same keys, limits, masking and audit as any other connection.

For AI agents

Let an agent query your data, governed like an app

An agent with a database password is an agent with everything. Through the MCP server it gets saved queries as tools, ad-hoc SQL only where you allow it, descriptions of what tables mean, and writes only with a person approving.
