For SaaS products

Put analytics in front of your customers, one tenant at a time

Customers want their own numbers inside your product. Building that usually means an analytics backend with tenant isolation you have to get exactly right. Here, each user signs in with the token your app already issues, and the tenant comes from that token, never from the request.

✓from_claim fills tenant_id from the verified token. A user who sends one anyway gets 400; a token without the claim gets 403.
✓QUERYAPIGATE_JWT_ROLE_CLAIM maps a claim such as plan to a role, so each plan gets its own queries, rate limit and quota, counted per user.
✓cache_ttl per query, keyed on each caller's own values, so tenants never share a cached response. ClickHouse or DuckDB underneath for dashboards that load fast.
✓CSV or XLSX for the download button, and every user's runs recorded as jwt:<user>.

For internal tools and dashboards

Back an internal app without a backend team

A frontend needs six queries from three databases. That is six endpoints, three drivers and one more service to keep alive. Or it is six saved queries, one key with JWT sign-in for your app's users, and CORS.

✓App users sign in with your existing JWT (JWKS); a from_claim parameter fills the filter from their token, so each person sees their own rows.
✓Queries across PostgreSQL, ClickHouse and a bucket of Parquet behind one base URL and one key.
✓A cache_ttl per query, shared through Redis when you run more than one instance.
✓Pagination, eight output formats and ?stream=true for the CSV download button.

For operational workflows

Let a partner or a form write, through one approved query

Sometimes the job is putting data in: a partner submitting orders, a form filing a request, a support lead correcting a record. Writing is off by default at every level, and you open one query, for one caller, and nothing else.

✓QUERYAPIGATE_ALLOW_WRITES is the server-wide ceiling: until it is set, nothing writes, whatever a key says.
✓A key or role writes only with allow_writes, which allowed_write_ops can narrow to insert, update or delete.
✓Or make exactly one saved query writable for one key. Every other query, and ad-hoc SQL, stays read-only.
✓Values are typed and bound, never SQL, and every write is in the run history. For AI agents, each write waits for a person to approve it.

For a partner or customer

Hand a partner one query, not your schema

A customer wants their orders. The usual answer is a bespoke endpoint, an auth middleware and a quarter of review time. The alternative is a scoped key that can call exactly one saved query, written for their rows.

✓A queries grant names saved queries; it reaches nothing else on the connection, not even the schema.
✓Masking rules on the key hash or hide columns like email, whatever the SQL calls them. Partners who sign in through your identity provider can share one query instead: a from_claim parameter takes customer_id from their token, never from the request.
✓Rate limit, IP allow-list and expiry on the key. Rotate its secret with a grace period when it leaks.
✓Their /openapi.json lists only the one endpoint they can call. Put it in a collection and they get a Postman collection too.

For pipelines and partners' buckets

Deliver a daily file, incrementally, to someone else's bucket

Every night a partner needs yesterday's changes as Parquet in their S3 bucket. Writing that job means credentials, retries, a watermark and a place to see when it failed. A saved export is all of those.

✓A destination is an s3://, gs:// or r2:// prefix with credentials stored like a connection password. Every write is locked to that prefix.
✓Incremental: the largest updated_at delivered last time is bound to :since next run. The watermark moves only after the file is written.
✓One run at a time per export; a crashed run cannot hold the lease forever. The export_failing alert fires while the newest run failed.
✓Scheduling stays with what you have: cron, a Kubernetes CronJob, Airflow.

For operations screens

A live view of what is being queried, by whom

A wall display or a client that reacts when a query runs. GET /events streams each run as it completes, per key if you want, fanned out across instances by the events server.

✓Server-sent events over plain HTTP: a fetch stream in the browser with the key in a header, no WebSocket infrastructure.
✓Per-key feeds, so a partner can watch their own calls and nobody else's.
✓Across several instances, queryapigate events reads every instance's runs from the shared store, woken by a PostgreSQL notification.
✓Stable since 0.34, under the compatibility promise. Filter by query, connection, kind or status.

For data and analytics leads

Self-serve data for every team, without handing out the database

Ten teams want data from the warehouse. Shared database passwords leak, and routing every request through the data team as a ticket doesn't scale. Publish saved queries in collections instead, give each team a role, and let people find what they can use.

✓A role per team: the collections it may run, its rate limit and quota. Keys are made from the role, or people sign in through your identity provider and are mapped to it.
✓A collection groups saved queries. Granting one is read-only and reaches exactly the queries in it, nothing else on the connection.
✓GET /catalog shows each caller what it can call and on what terms: description, parameters, whether it is cached or writable, and its own rate limit.
✓Descriptions imported from database comments say what each column means, and every run is attributed to the team that made it.

For data teams

Turn a bucket of Parquet into a queryable API

The lake has the data; the people who need it have a browser and curl. A DuckDB connection pointed at a prefix makes each file a view, locked to the paths you list, with no copy and no warehouse.

✓Parquet, CSV and JSON on S3, GCS, R2, HTTPS or disk. Hive-style key=value/ partitions become one view.
✓Nothing outside allowed_paths can be read, enforced by DuckDB itself as the connection opens.
✓Saved queries over the views get grants, masking and caching like any other.
✓Results back out as Parquet too, in steady memory at any size.

For legacy and vendor databasesEXPERIMENTAL

Put a governed API in front of a database you can't change

The core system runs on Oracle, SQL Server or DB2, and nobody wants to touch it. Generic JDBC loads the vendor's own driver, so that data can be served through saved queries with the same keys, limits, masking and audit as any other connection.

✓A jdbc connection takes the vendor's driver .jar, its driver class and a JDBC URL. Run the image's -h2 variant, which includes Java.
✓Saved queries, grants, masking, quotas and the audit log work as they do on every other connection.
✓Known limits, verified: no query time limit (set one in the database), and no table allow-lists or schema browser on JDBC connections.
✓Experimental: CI tests JDBC with H2's driver standing in for a vendor. Connect with a database user that can only read.

For AI agents

Let an agent query your data, governed like an app

An agent with a database password is an agent with everything. Through the MCP server it gets saved queries as tools, ad-hoc SQL only where you allow it, descriptions of what tables mean, and writes only with a person approving.

✓Any MCP client connects to /mcp, with an API key or OAuth 2.1 through your identity provider.
✓The same grants, limits and masking as REST. An agent cannot be governed less because of its protocol.
✓Descriptions imported from the database's own comments tell the agent what ltv_90d is, so it writes the right SQL first time.
✓Per-agent usage, and an alert when one reads ten times its usual hourly volume, above a floor you set.

Answer the auditor from the running system

For platform teams

Run it like the rest of your platform

The platform team wants it installed with Helm, changed through a pull request, and holding no database password of its own. Each of those is a setting, not a project.

✓The whole setup as one YAML file with no secret in it. config diff on every pull request, config apply on merge, all or nothing.
✓QUERYAPIGATE_CONFIG_LOCKED keeps what the file manages to the file; a change made by hand on prod is refused, not drifted.
✓A Helm chart for one pod or several: non-root, read-only root filesystem, and with the chart's config option a merge is the deploy.
✓No password at rest: short-lived credentials from Vault per lease or RDS IAM tokens, or ${vault:…} and ${aws-sm:…} references. AWS experimental.
