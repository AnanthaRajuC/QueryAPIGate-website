01 · Identity and access

Your identity provider decides who administers it

People sign in through your SSO and get a role from your groups. Services, partners and AI agents each get exactly the queries they need, and no more.

Single sign-on

Console sign-in through OIDC

Authorization code flow with PKCE, as a confidential client: the browser never holds a token. People are bound by the provider's sub, and their role comes from their groups at every sign-in. QUERYAPIGATE_SSO_ONLY removes personal tokens so nobody routes around your MFA.

Guide 48 →
Break-glass

A way in when the provider is down

The shared admin key stays an owner for emergencies. Once a named owner exists, every use of it is logged, audited as break_glass_used and alerted. The last active owner can't be locked out by accident.

Threat model →
Leavers

Off in your IdP, off here

Someone removed from your groups loses their role at the next sign-in; a session already open lasts until it expires (8 hours by default). Deactivating them in QueryAPIGate ends it at once.

Named administrators →

Four fixed administrator roles

Every management operation needs one capability, checked before the route runs; a test fails if an operation has no entry, so a new route can't ship unguarded. Roles bound what an administrator can change. For data, the database account behind each connection is still the backstop.

ownerEverything, including administratorsAny SQL, every connection
adminConnections, API keys and roles, queries, cacheAny SQL, every connection
developerSaved queries and collectionsAny SQL, every connection

Partners and services

Scoped keys, least privilege by default

Grants per saved query, collection or connection; read-only unless writes are granted; table allow-lists; IP allow-lists; expiry; rotation without downtime; rate limits, quotas and concurrency caps per key.

Your applications' users

Tokens from your identity provider

Signed-in users call with a JWT checked against your JWKS. A parameter can be bound from a claim, so a user's tenant_id or email comes from the token, not the request.

Governed like any other caller

MCP clients sign in through OAuth 2.1 or use a scoped key, and see only the saved queries they are granted. A write proposed by an agent waits for a person to approve it, and both are audited.

02 · Audit and monitoring

Who changed what, in a record your SIEM already holds

Every configuration change is in a hash-chained audit log, signed with a key kept outside the store and streamed to your SIEM, so a later rewrite contradicts a copy someone else holds.

Tamper-evident

A signed hash chain

Each entry's hash covers the one before it, so changing, removing, inserting or reordering an entry breaks every hash after it. With QUERYAPIGATE_AUDIT_KEY the chain is HMAC-signed with a key outside the store. The server checks it every 5 minutes.

To your SIEM

Syslog over mutual TLS, or OTLP

Each entry is sent with its sequence number and hash. Tested on every push against rsyslog, syslog-ng and the OpenTelemetry Collector, including refused certificates and an outage. Stable since 0.32.

Guide 53 →
Run history

Every call, attributed

Who ran which query version, from which front door, with status, rows and duration. Parameter values are never recorded.

Metrics, alerts and traces

Prometheus metrics per key, a Grafana dashboard, 25 kinds of alert, request IDs in structured logs. OpenTelemetry tracing is experimental.

Upgrades

Every store upgrades itself

Each release upgrades the store on its first start. Several instances on one store are replaced one at a time with no downtime, checked in CI against the previous release. Patch releases never break a covered surface; minor releases say so under Breaking.

Upgrade safely →Versions →

Backup and restore

Everything QueryAPIGate owns, from connections and saved queries to keys, roles, history and the audit log, lives in its store. Back it up while it serves; restore one now and then, because a backup nobody has restored is not a backup.

Kept out of a backup on purpose: QUERYAPIGATE_SECRET_KEY, which encrypts connection passwords, the admin key, and any environment variable a connection refers to. Keep them in your secrets manager. Scoped keys are in the store as hashes, so they keep working after a restore.

Back up and restore →Deployment guide →
# SQLite: a consistent copy while the server keeps running
$ queryapigate backup /data/backup.db --force

# PostgreSQL: one snapshot, safe while serving
$ pg_dump --format=custom --schema=public --no-owner --no-privileges \
    --file="queryapigate-$(date +%F).dump" "$QUERYAPIGATE_DATABASE_URL"
04 · Cryptography and supply chain

Approved algorithms, and releases you can verify before they run

Every algorithm is FIPS-approved, and a test fails if the code gains one that isn't. Every release since 0.31 is signed, with an SBOM and provenance you can check by digest.

FIPS 140-3

Validation is a property of the cryptographic module, not of the application. QueryAPIGate uses only FIPS-approved algorithms (FIPS 140-3, SP 800-131A); run it on a validated OpenSSL in FIPS mode, such as Red Hat Enterprise Linux 9 with fips=1 or Ubuntu Pro FIPS, with Python's cryptography from the distribution, and the cryptography it uses is validated.

Signed releases, SBOM and provenance

The image and the Helm chart are signed keyless with cosign by the release workflow, by digest. Each platform carries an SPDX 2.3 SBOM and SLSA provenance naming the repository, workflow, commit and run. Every GitHub Action is pinned by commit and the base images by digest.

$ cosign verify ghcr.io/anantharajuc/queryapigate:0.34.2 \
    --certificate-identity https://github.com/AnanthaRajuC/QueryAPIGate/.github/workflows/docker.yml@refs/tags/v0.34.2 \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com

$ docker buildx imagetools inspect ghcr.io/anantharajuc/queryapigate:0.34.2 --format '{{json .SBOM}}'

Admit only signed releases to a cluster with Sigstore's policy-controller or Kyverno; both policies are in the guide, tested against signed, unsigned and wrongly signed images.

The project's own security practices are scored by OpenSSF Scorecard, an independent automated check from the Open Source Security Foundation. It runs on every change to the main branch and once a week, and the badge below always shows the latest score.

No SOC 2 or ISO 27001 report

Those certify an organisation running a service. QueryAPIGate runs inside yours, under your controls; what it provides is the evidence your own assessment needs.

Experimental features are labelled

Today: H2, generic JDBC and MongoDB connections, OpenTelemetry tracing, and secrets and credentials from AWS. They sit outside the compatibility promise until they graduate.
