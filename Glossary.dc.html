Glossary

The words QueryAPIGate uses

48 terms you meet across the docs, the Console and the guides, each defined in a sentence or two and linked to the page that covers it.

ABCDEFGLMPQRSTW

A

#Ad-hoc SQL

SQL a caller sends directly to /execute_sql or the MCP execute_sql tool, rather than a saved query. Only for keys granted a connection, one statement, read-only unless allowed, and confined to allowed_tables.

Read more →
#Admin roles

The four fixed administrator roles: owner (everything), admin (everything but administrators), developer (saved queries and collections, no keys) and auditor (read only, no SQL).

Read more →
#Administrator

A named person or pipeline that manages QueryAPIGate, holding one of four fixed roles and signing in with their own admin tokens, so every change in the audit log has someone behind it.

Read more →
#Agent writes

How an AI agent changes data: only through a saved query its author marked agent_writes, either held for a person’s approval (approval) or as a single idempotent insert (insert).

Read more →
#Alerts

Live conditions worked out on each request, such as key_expiring or writes_awaiting_approval, shown in the Console and at GET /api/v1/alerts, and gone once the cause is.

Read more →
#allowed_tables

A grant that confines a key’s ad-hoc SQL to named tables. The SQL is parsed, not pattern-matched, and a table outside the list answers as if it did not exist.

Read more →
#API key

The credential an application calls with, sent as X-API-Key. Stored only as a SHA-256 hash; it can be scoped, rate-limited, pinned to IP ranges, given an expiry and rotated.

Read more →
#Approval (write request)

A held agent write, wr_…, that an administrator with writes.approve approves or rejects in the Console. Once approved it runs once, for that caller, with exactly the arguments shown, before it expires.

Read more →
#Audit log

The record of every administrative change: who changed what, with the fields that changed. Each entry is chained to the one before, and the log can stream to your SIEM.

Read more →

B

#Break-glass key

QUERYAPIGATE_API_KEY: a full-access key that keeps working as an owner when the identity provider is down. Its use raises an alert.

Read more →

C

#Catalogue

GET /catalog: what the calling key may run, and on what terms, such as whether a query is cached, whether this key may write through it, and its rate limit.

Read more →
#Collection

A named group of saved queries. A key or role granted a collection reaches every query in it, including ones added later; it can be renamed, exported, imported and handed out as a Postman collection.

Read more →
#Column masking

Hiding a column from a caller: hash, mask, null or drop. Traced through aliases, CTEs and joins to the source column; a query whose columns can’t be traced is refused rather than answered unmasked.

Read more →
#Compatibility promise

What changes only with notice: REST endpoints and responses, CLI commands, environment variables, the storage format, grant fields, the saved-query format, the MCP tool contract and error codes.

Read more →
#Configuration as code

config export, config diff and config apply: the whole setup as one YAML file with no secret in it, reviewed in a pull request and applied all or nothing.

Read more →
#Connection

A named database, or a folder or bucket of files, that QueryAPIGate reaches with its own credentials. Callers never see those credentials.

Read more →
#Console

The built-in administration UI at /console: connections, saved queries, keys and roles, a SQL editor, history, the audit log, alerts and approvals. Everything it does is also on the Management API.

Read more →

D

#Data dictionary

An MCP resource per connection, queryapigate://connections//dictionary, telling an agent what each table and column means and which columns are masked for it.

Read more →
#Descriptions

Plain-language notes on connections, tables, columns and parameters, imported from database comments or written by you, and given to agents and docs alike.

Read more →
#Draft and published

A saved query has at most one published version: the one /q/ runs and OpenAPI, MCP and Postman describe. Newer versions are drafts, invisible to callers until published.

Read more →

E

#The eight stages

What every call passes, whichever front door it used: identify the caller, apply its limits, check the grant, validate parameters, guard the SQL, run it, mask and format, record it.

Read more →
#Error code

The stable code field on every error, such as param_invalid or forbidden. Part of the compatibility promise: an existing code is never renamed or repurposed.

Read more →
#Example APIs

Four worked scenarios installed by queryapigate examples load: reporting, dashboard data, a streaming export and a partner integration, each with a collection, a role and a ready key, removable with one command.

Read more →
#Experimental

A feature that works but sits outside the compatibility promise until it graduates, labelled wherever you meet it.

Read more →
#Export

queryapigate export or a saved export: a full result written to a file or a bucket through the same streaming path, incrementally from a watermark, with no server needed.

Read more →

F

#from_claim

A parameter whose value comes from the caller’s sign-in token instead of the request, so a user can only ever ask for their own rows. A caller who sends it anyway is refused.

Read more →
#Front door

One of the ways a call arrives: REST, MCP, live events, exports or the Management API. All of them pass the same governance code.

Read more →

G

#Grant

What a key or role may reach: whole connections, named saved queries or collections, tables for ad-hoc SQL, and which writes, if any.

Read more →

L

#Live events

Server-sent events as saved queries run, per key if you want, from GET /events or the separate queryapigate events server for many clients.

Read more →

M

#Management API

/api/v1: everything the Console does, over HTTP, for scripts and pipelines.

Read more →
#MCP

The Model Context Protocol, the standard AI agents use to call tools. QueryAPIGate’s MCP server publishes saved queries as tools under the same rules as REST.

Read more →
#MCP tool

A published saved query as an agent sees it: a name, a description, an input schema built from its parameters, and structured results. mcp: false hides a query from MCP while it still serves REST.

Read more →

P

#Parameter rules

What a :name parameter accepts: type, default, required, enum, numeric range, length and pattern. Values are bound, never spliced into SQL, and a request breaking a rule gets a 400 listing every problem.

Read more →

Q

#Quota

Calls and rows per day or month for a key, with X-Quota-Remaining-* headers on every response and an alert before it runs out.

Read more →

R

#Rate limit

A request budget: a server-wide limit by client address, and an optional per-key rate_limit. A request must pass both; over it, the answer is a 429 with retry_after.

Read more →
#Request ID

An identifier on every response, X-Request-Id, also in the error body and on every log line written for that request.

Read more →
#Response cache

Optional HTTP caching a saved query opts into with cache_ttl: ETag, conditional requests and 304, never for a query that writes. In-process, or shared through Redis.

Read more →
#Role

A reusable template of grants and limits, copied onto a key once when the key is created. Editing or deleting a role later never changes a key made from it.

Read more →
#Run history

The record of each run: when, which connection, which key, through which front door, how long and how many rows. MCP runs carry "transport": "mcp".

Read more →

S

#Saved query

SQL with a name, description, parameters, permissions and optional cache settings, published as GET /q/, an MCP tool and an export from the one definition.

Read more →
#Scoped key

An API key restricted to a set of connections, an allow-list of saved queries or collections, or both, so it reaches only what it was given.

Read more →
#Signed-in user

An app user who calls with their own Authorization: Bearer token from your identity provider instead of a shared key, and is mapped to a role.

Read more →
#SQL guard

The check that lets only single SELECT, WITH, SHOW, DESCRIBE and EXPLAIN statements through by default, before anything reaches the database.

Read more →
#Store

Where QueryAPIGate keeps its own state: saved queries, keys, roles, history and the audit log. A SQLite file by default, or PostgreSQL for several instances.

Read more →
#Structured results

An MCP tool’s answer as data: structuredContent matching its outputSchema, {"rows": [...], "truncated": }, so code reads rows rather than parsing text.

Read more →

T

#Tier 1

The database types with every feature, tested against a real server in CI and covered by the compatibility promise.

Read more →

W

#Workspace

An experimental way to run several teams on one server, each with its own connections, queries, keys, roles, history and audit entries. Every route also answers at /w//….

Read more →
#Write granularity

allowed_write_ops: narrowing a key that may write to specific operations, such as only INSERT, or only on one curated query.

Read more →
