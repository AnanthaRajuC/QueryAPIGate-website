One MySQL server, six services, one gateway

A database per microservice on one MySQL server, and queries that read across them - a customer, their orders, their payments. Measured with TPC-C's data split into six databases, five rounds per comparison, and the harness published so you can rerun it.

03 · Threads

Fast queries want fewer threads.

Extra threads compete for Python's interpreter lock. A 0.03 ms lookup is fastest with one thread, 28% faster than eight. A 0.42 ms query wants two, so one call can run while another waits on MySQL. Slow reports and exports are the opposite case, and that's what the eight are for.

On 0.42, threads beyond two cost throughput: each added thread meant more pings, and each ping stopped every thread. On 0.43 the ping is gone and threads overlap the waiting: four serve 730 calls a second, 46% more than 0.42's best. With MySQL across a network, use 4.

04 · Busy users

When a few users make most of the calls.

With skewed traffic, a 30 s response cache answered 59% of calls, raised throughput 23%, and sent 58% fewer statements to MySQL. With uniform users it cost 8%: almost nothing repeats within 30 seconds, and storing it buys nothing. Put cache_ttl on what your users repeat: dashboards, popular accounts.

05 · Across a network

Two round trips, and the store.

Counted with MySQL's statement log, and measured by timing calls at increasing network delay. 0.42 made a third: a ping mysql-connector sent before every query, while holding Python's interpreter lock, so every thread waited for it. 0.43 reuses the cursor, and the ping is gone. With 32 callers and MySQL 0.5 ms away, that's 52% more calls a second (680 against 446).

Every call reads three of QueryAPIGate's own rows - the API key, the saved query, the connection. With several instances on a shared PostgreSQL store, those reads cross the network too. The metadata cache keeps them in memory, and takes the store off the network entirely.

It caches rows, never decisions: whether a key is active, expired or allowed from this address is checked on every call. A change made on another instance takes up to the TTL to arrive.

Several instances

On a shared PostgreSQL store, workers scale as they do on SQLite: 625 to 1,862 calls a second from 1 to 8 workers, or 720 to 2,270 with the metadata cache, which also cuts the store's load to a third. A core's second hyperthread is worth about 0.6 of a core here, so run one worker per physical core.

06 · Keeping services apart

Closed in 0.43.

A key's table allow-list matches database.table on MySQL now, as it does on every SQL connection: a bare grant means the connection's own database.

Still good practice: a MySQL user per service, with SELECT on its own databases only, so MySQL enforces it too.

08 · How it's measured

Measured, not promised.

  • Every part on its own cores: the gateway, MySQL 8.4 and the load generator, on a 20-thread laptop on AC power. A /health check around every block showed whether the machine changed speed. One session, 2026-10-26 18:32 to 21:59, on the same laptop and data as the first run.
  • Builds take turns in a rotating order, 5 rounds per comparison. A difference counts only when the min-max ranges don't overlap; by chance, that happens under 1% of the time.
  • Direct baseline: sysbench sent the same SQL straight to MySQL, over TLS like the gateway's driver.
  • Real skew: 600,000 users drawn uniformly, or from a Zipf distribution for the busy-user test.
  • 9.65 million requests, every one returned 200.
What it doesn't cover
  • one machine, not separate hosts;
  • data in memory, so every query is cheap;
  • a simulated network;
  • no TLS termination, load balancer or Redis in front;
  • reads only, no writes;
  • a burst of about 30 ms every few seconds at light load (p99.9), measured but not yet explained.

TPC-C-derived: the data and two queries (Order-Status, Stock-Level) are TPC-C's, but this is not the TPC-C benchmark, and these are not TPC-C results.

09 · Reproduce

Run it on your own machine

It starts its own MySQL, loads the data with go-tpc, splits it into the six databases, pins each part to its own cores, and compares releases side by side. About 3½ hours.
