Deploy

Deploy it your way

Every way of running QueryAPIGate uses the same server; the shapes differ only in which parts you add around it. Start with one container and a file on disk. Add PostgreSQL and Redis when you need more than one instance, and add the Rust data plane and a ClickHouse run store when traffic calls for it. You don't rewrite anything or move your queries, and your API keys and URLs stay the same.

550 / 650Per worker: the sizing figure at about 4 ms p99, which is 75% of capacity. 650 is with QUERYAPIGATE_METADATA_CACHE_TTL.
2 threadsBest for fast queries, 13% ahead of the image's default of 8. Keep 8 or more for slow queries, exports and /events.
Workers needed = the larger of (calls a second ÷ 550) and (calls a second ÷ threads ÷ (query time + round trips × network RTT)), plus one you can lose. A 0.03 ms lookup is limited by CPU. A 20 ms report query is limited by waiting: 8 threads serve about 340 a second. Size yours on the Performance page →

Helm chart

Guardrails, not surprises

The Helm chart refuses to install a shape that would quietly misbehave, and says why in its own words:

helm install · what the chart refuses
✕
replicas: 3 · store.type: sqlitestore.type sqlite keeps the store in one file on one volume - it runs one pod.
✕
replicas: 3 · no RedisMore than one pod needs Redis, or rate limits, max_concurrent and quotas are counted per pod.
✕
store.type: postgres · no database URLstore.type postgres needs QUERYAPIGATE_DATABASE_URL in secret.values (or in your existingSecret).
✕
config: · QUERYAPIGATE_API_KEYQUERYAPIGATE_API_KEY is a secret: put it in your existingSecret or secret.values, not config - config is plain text in the Deployment.
You find out at helm install, before anything changes in your cluster.
