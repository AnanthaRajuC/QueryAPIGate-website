Deploy

Three reference architectures, each one tested in CI

Start with one instance on SQLite. Move to several on PostgreSQL and Redis when you need availability, or install the Helm chart. Instances are interchangeable, so moving between shapes is a configuration change, not a migration project.

Install optionsDeployment guide

Choose a shape

All three run the same image and the same code. Each is exercised on every change: three real servers behind a load balancer, and the chart installed and upgraded under load on a real cluster.

Start here

Single instance

  • →One container or process; SQLite store on a volume, or PostgreSQL.
  • →Restart on failure; back up the store on a schedule.
  • →Redis optional, for a cache that survives restarts.

Several instances

High availability

  • →PostgreSQL store and Redis: everything an instance owns is shared, so any instance answers any request.
  • →Rate limits, quotas and concurrency caps counted across instances.
  • →Rolling upgrades; queryapigate events fans live events out to many clients.

Helm chart

Kubernetes

  • →One pod on SQLite, or several on PostgreSQL and Redis behind a disruption budget.
  • →Non-root, read-only root filesystem, no capabilities; a NetworkPolicy and autoscaler if you want them.
  • →The chart refuses setups that can't work, such as several pods without Redis.

Measured, not promised

One container runs one worker with eight threads; add containers for capacity. These are the numbers the project has measured and checked in.

~2 msAdded by a saved-query call over ad-hoc SQL on a 100-row table (MySQL, p50 6.4 ms vs 4.1 ms).
~300 req/sPer instance at five concurrent callers, one worker with eight threads (MySQL and ClickHouse).
Flat memoryStreaming 1M rows: about 0 MB extra, against 337–988 MB buffered (MySQL).
2.5×Faster on a cache hit than a miss: 5.8 ms vs 14.2 ms median (MySQL).
~1 msTracing cost per request with every request traced; nothing measurable at 10% sampling.
1,016 / 1,000Calls served against a 1,000-call quota on two instances under load, sharing Redis.

Measured with the scripts in benchmarks/ against real databases over real HTTP, between 24 and 30 September 2026; tracing and quota figures from the 0.23 and 0.24 release measurements. Absolute numbers depend on the machine; the shape is the portable claim. The full reports are in benchmarks/results.

Production checklist

The steps between a running server and one you would put in front of a partner.

  • 1Put it behind TLS: a reverse proxy, with QUERYAPIGATE_TRUST_PROXY set to the number of proxies.
  • 2Give people their own admin access and seal the shared key: guide 43.
  • 3Encrypt stored passwords, or use no passwords at all: guide 22, guide 56.
  • 4Protect /metrics and limit ${VAR} references: guide 58.
  • 5Scrape metrics and wire up alerts: guide 35; traces: guide 51.
  • 6Stream the audit log to your SIEM: guide 53.
  • 7Back up the store and rehearse a restore: guide 33.
  • 8Run only signed releases, pinned by digest: guide 59; upgrade with guide 34.
