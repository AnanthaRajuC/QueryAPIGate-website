Every major database, one interface

Tier 1 types get every feature, are tested against a real server in CI and sit under the compatibility promise. Experimental types work, with documented gaps. The same guard, pooling, parameter binding and output formats apply to every one; what each supports is in the support matrix.

Pooling and time limits

Idle connections kept per connection, QUERYAPIGATE_POOL_SIZE, and a query time limit enforced on every front door (on every database type but generic JDBC), lowered per key or per request with ?timeout.

TLS to the database

PostgreSQL's sslmode and MySQL's ssl_* settings are passed to the driver: a connection that asks for a verified certificate fails rather than connecting without one.

Passwords as ${VAR} references or encrypted at rest under a key you can rotate; or short-lived credentials from Vault or RDS IAM Exp.

02 · Security and access controlPathGive a partner an API →

Access control, per key, decided before any query runs

Built to expose specific query results, not database credentials. A key identifies an application; every grant below narrows what it reaches, and writes are off by default. Hand an external client a key that can only ever reach one named query while internal callers keep connection-level access.

The eight stages every request passes, step by step →
QueryAPIGate ~ security · every control a key carries

Whole connection

connections

Every saved query on it, plus ad-hoc SQL if allowed.

Curated endpoints

queriescollections

Name the saved queries a key may run, one at a time or as a collection. Nothing else answers.

Table allow-list

allowed_tables

Ad-hoc SQL confined to named tables; the SQL is parsed, not pattern-matched.

Column masking

mask

Hash, mask, null or drop named source columns. Traced through aliases, CTEs and joins; refused rather than served unmasked.

Write granularity

allowed_write_ops

Writes off by default. Turn on only INSERT, or UPDATE on one query.

Budget and origin

rate_limitallowed_ips

A per-key request budget on top of the server-wide, IP-keyed limit (a request has to pass both), and a list of IPs or CIDR ranges the key may call from.

Lifecycle

expires_atlast_used_at

Time-boxed keys for trials and contractors; alerts before expiry and for keys gone unused.

Signed-in users

Authorization: Bearer

Accept the JWT your app already has (Auth0, Cognito, Keycloak, Azure AD or your own secret). Each user calls as themselves, mapped to a role.

Fair shares

max_concurrentquery_timeoutmax_rows

Cap the queries a key runs at once, how long each may run and the rows a call returns, across every instance. Over it: 429 too_many_concurrent.

Usage quotas

quota

Calls and rows per day or month, with X-Quota-Remaining-* headers on every response and an alert before it runs out.

Secret rotation

rotate

Reissue a key's secret while the old one keeps working for a grace period, or zero for a leaked one.

Administrators and sign-in

owner · admin · developer · auditor

The people and pipelines that manage the server are named, with the narrowest role that fits, so every change in the audit log has a person behind it.

Single sign-on and the break-glass key →

Keys and passwords at rest

API keys are stored as SHA-256 hashes, never the raw secret. Database passwords are encrypted under QUERYAPIGATE_SECRET_KEY and decrypted only in memory when a connection opens; a literal password on disk is never returned to a client either way.

Security →

Scoped keys

Restrict a key to a set of connections, to an allow-list of saved queries independent of any connection grant, or both. A query in that list can be curated for write access without granting it anywhere else the key reaches.

Guide 1 →

Named permission roles

A reusable template of connections, write access, queries, collections, rate limit and allowed IPs, copied onto a key once at creation. Editing or deleting a role afterwards never affects a key already created from it.

Collections

File saved queries into named groups and grant a key a whole group, live. Every move that changes who can reach a query is audited with the keys that gained or lost access. Rename without any key losing reach; export a bundle and import it elsewhere.

Guide 7 →

Workspaces EXP

Several teams on one server, each with its own connections, saved queries, keys, roles, destinations and exports, and its own history, audit entries, alerts and events. Every route also answers at /w/<workspace>/…; a key works in its own, and a workspace's owner manages its members. ADR 0023 →

The SQL guard

Only single SELECT, WITH, SHOW, DESCRIBE and EXPLAIN statements pass by default, with bound :name parameters rather than string-concatenated SQL. Ad-hoc SQL, where a key is allowed it, is confined to allowed_tables and recorded like any saved query.

03 · MCP server for AI agentsPathAgents →

Let an agent query production data without handing it a database connection

The same saved queries are tools an AI agent can call over the Model Context Protocol, served by a dedicated process, queryapigate mcp. It is the same governed core as REST: an agent gets the same identity, grants, column masking, limits and audit as any app, enforced in the gateway and never asked of the model.

The MCP server reference →
QueryAPIGate ~ mcp · what an agent sees

One tool per published query

What an agent sees in tools/list: the parameters, their types, bounds and an example, and the tables the query reads, so each argument means something rather than being just a name.

tools/listread-only
{
  "name": "example_top_films",
  "description": "Top films by rentals in a category",
  "inputSchema": {
    "properties": {
      "category": {"type": "string", "enum": ["Comedy", "Drama", "Action", …]},
      "top_n":    {"type": "integer", "minimum": 1, "maximum": 50, "default": 10}
    }
  },
  "annotations": {"readOnlyHint": true}
}
// the same query that answers GET /q/example_top_films over REST

Self-describing tools

Each published query is an MCP tool carrying its parameters, their types, descriptions and an example, and the tables it reads. A query can be hidden from MCP with mcp: false while it keeps serving over REST.

Read-only by default; writes with approval

The ad-hoc execute_sql, list_tables and describe_table tools are forced read-only whatever the key's own write grant. An agent's writes are held as requests and run only once a person approves them, with exactly the arguments shown.

Masking-aware metadata

describe_table and schema discovery honour column masking: a masked or dropped column is flagged, never shown as readable, so an agent cannot even learn that hidden data exists.

Standard OAuth

The MCP server is an OAuth 2.0 protected resource (RFC 9728). An agent signs in through your identity provider, and the token's audience is bound to the MCP server's own URL, so it cannot be replayed against REST or the database.

Every call recorded

MCP runs land in the same run history, per-key metrics and tamper-evident audit log as every other caller.

Connect a client

Claude Desktop, Cursor, LangChain or any MCP client: point it at the server, sign in, and the published queries appear as tools.

04 · Saved, versioned queries

From a SQL statement to a documented endpoint

A saved query bundles SQL, name, description, parameters, author, version, permissions and optional cache settings into one addressable resource, GET /q/<name>. Saving again under the same name creates a new version rather than overwriting the old one, so a change to the SQL never silently changes what is already live; ?version=1 still runs the prior one, and every run is recorded in the query's history.

QueryAPIGate ~ queries · from a statement to an endpoint

Saved queries as endpoints

Each saved query is versioned, has typed parameters with ranges and lengths, and keeps a run history. OpenAPI and a Postman collection are generated, and OpenAPI Generator turns the spec into a typed client in about 50 languages. Group queries into collections and grant access to the whole collection at once.

curl
$ curl 'http://127.0.0.1:5000/q/example_top_films?top_n=2&category=Comedy&format=csv' \
    -H 'X-API-Key: demo-key'
title,category,rating,rentals,rank
Electric Signal,Comedy,PG,977,1
Crimson Garden,Comedy,PG-13,631,2

Versions, drafts, publishing

Every saved query has at most one published version: the one /q/<name> runs and the one OpenAPI, MCP and Postman describe. Newer versions are drafts, invisible to callers until published; the admin key can test one by number. Roll back to any earlier version. Older versions stay runnable with ?version=.

05 · Bound query parameters

Values bound, never spliced into the SQL

SELECT * FROM film WHERE film_id = :id answers GET /q/film_by_id?id=7. Values travel to the database separately from the SQL text, so they cannot be injected into it. A parameter can declare a type, default, required or optional, enum, numeric range, length and pattern; invalid input is rejected with a field-by-field 400 before it reaches the database.

QueryAPIGate ~ parameters · checked before the database
query_parameters.json
// query_parameters
{
  "rating":     {"type": "str", "enum": ["G","PG","R"], "default": "PG"},
  "max_length": {"type": "int", "min": 1, "max": 600},
  "title":      {"type": "str", "required": false, "pattern": "[A-Za-z ]+"},
  "customer":   {"type": "int", "from_claim": "sub"}
}
Try itEdit the values. The checks below run exactly as the rules above say, before anything reaches the database.
response
$ curl '/q/films?{{ tp.qs }}' -H 'X-API-Key: demo-key'
{{ tp.status }} {{ tp.body }}

Typed parameters, checked before the database

Each :name in the SQL is a bound parameter with a type, bounds, length, enum, pattern and default. A request that breaks a rule gets a 400 listing every problem and never reaches the database. from_claim takes a value from the caller's sign-in token instead of the request, so a user can only ever ask for their own rows.

07 · Pagination and streaming

Page what people read, stream what pipelines take

?page=2&page_size=50 pages results, with X-Has-More telling the caller whether more exist. For full exports, ?stream=true with CSV, TSV or NDJSON streams the entire result straight from the database cursor rather than buffering it, verified end to end with 1,000,000-row results on MySQL, PostgreSQL and ClickHouse.

The measured numbers →
QueryAPIGate ~ streaming · three ways to take a result
paging and streaming
$ curl '/q/example_rentals_since?since=2026-01-01&page=2&page_size=50' -i -H 'X-API-Key: demo-key'
HTTP/1.1 200 OK
X-Has-More: true
X-Row-Count: 50

# 1,000,000 rows, straight from the database cursor, flat server memory throughout

$ queryapigate export example_rentals_since --out '/exports/{name}_{date}.csv'
# the same streaming path from cron, systemd or a Kubernetes CronJob; no server needs to be running

Paging

?page= and ?page_size= for typical results, with X-Has-More and X-Row-Count headers so a client knows when to stop.

Streaming

Constant memory however large the result, in CSV, TSV or NDJSON, with a row ceiling you can set server-wide (QUERYAPIGATE_STREAM_MAX_ROWS, unbounded by default).

Streaming exports →

Scheduled exports

queryapigate export writes a full result to a file through the same streaming path, with no server running. Atomic rename on completion, non-zero exit on failure, deliveries to S3, GCS, R2 or disk that resume where the last run stopped.

08 · Query caching

HTTP caching a saved query opts into

A saved query can set cache_ttl and get Cache-Control, ETag, conditional requests and 304 Not Modified, plus an X-Cache: HIT or MISS header on every response. Never applied to a query that writes.

QueryAPIGate ~ caching · miss, hit, not modified
three requests
$ curl -i '/q/example_top_films?category=Comedy' -H 'X-API-Key: demo-key'
HTTP/1.1 200 OK
X-Cache: MISS
Cache-Control: max-age=300
ETag: "7f3a…"

$ curl -i '/q/example_top_films?category=Comedy' -H 'X-API-Key: demo-key'
HTTP/1.1 200 OK
X-Cache: HIT

$ curl -i '/q/example_top_films?category=Comedy' -H 'X-API-Key: demo-key' -H 'If-None-Match: "7f3a…"'
HTTP/1.1 304 Not Modified

Response cache

A per-query cache_ttl sets Cache-Control and ETag, answers conditional requests with 304 and reports X-Cache: HIT or MISS; never on a query that writes. In-process by default; with Redis, one cache shared by every instance, surviving restarts.

HTTP done properly

ETag and 304 Not Modified on cached responses, If-Match for safe concurrent edits, X-Has-More and X-Row-Count for paging, and ?timeout per request.

09 · Rate limiting

Different callers, different budgets

A server-wide, IP-keyed limit and an independent, optional per-key limit can both be in effect at once; a request has to pass both. Over a limit the answer is a 429 with the budget left in its headers.

QueryAPIGate ~ rate limiting · three callers, three budgets
Internal dashboardserver-wide limit onlyA generous IP-keyed budget set once with QUERYAPIGATE_RATE_LIMIT, no per-key limit.
Partner keyrate_limit: 200/hourIts own budget on top of the server-wide one; a request has to pass both.
Trial keyrate_limit: 20/hour · expires_atA small budget and an expiry date for an evaluation that ends on its own.

Server-wide

QUERYAPIGATE_RATE_LIMIT keyed by caller IP, enforced on every front door. With Redis, one budget across every instance; if Redis blinks, limits stay enforced per process.

Per key

rate_limit on the key, plus allowed_ips to pin it to addresses or CIDR ranges and expires_at to end it on a date.

Fair shares and quotas

max_concurrent, query_timeout and max_rows cap what one key can hold at once; quota counts calls and rows per day or month, with X-Quota-Remaining-* headers and an alert before it runs out.

10 · ObservabilityPathGo to production →

Every run recorded, every change audited

Structured JSON logs tagged with a request ID, per-query execution timing, slow-query warnings over a threshold you set, and Prometheus metrics at /metrics covering request and query counts and latencies, connection-pool occupancy and rate-limit rejections. Run history is per query and per key; the audit log records who changed what.

QueryAPIGate ~ observability · run history and alerts

Run history

When, which connection, which key, through which front door, how long, how many rows. Ad-hoc and MCP runs too.

Audit log

Timestamp, actor, action, target and the fields that changed, each entry chained to the one before. Secrets appear as "changed", never their value.

Request IDs

Every response carries X-Request-Id; every log line written for it carries the same.

Shown on the Console's Alerts screen, the bell in its header, and Home's System health. For paging, scrape /metrics with Prometheus.

Observe

Structured JSON logs with request IDs, slow-query warnings over a threshold you set, per-key metrics, a Prometheus /metrics endpoint behind a token, a bundled Grafana dashboard, and OpenTelemetry spans Exp from the request to the database call, never holding a value or a row.

Store

A SQLite file by default, or PostgreSQL for several instances. Versioned schema with upgrades tested in CI, backup and restore, passwords encrypted at rest.

Scale out

Redis, optional: one cache, one rate-limit budget and one event stream across every instance. If Redis blinks, limits stay enforced per process.

Deploy

pip, the image on ghcr (with an -h2 variant including Java), a Helm chart for one pod or several, and a multi-instance Compose setup behind Caddy. Non-root, read-only root filesystem.

Configuration as code

config export, config diff and config apply: the whole setup as one YAML file with no secret in it, reviewed in a pull request and applied all or nothing, by CI or at startup.

Secrets

Passwords encrypted at rest under a key you can rotate, or no password at all: ${file:…}, ${vault:…} and ${aws-sm:…} references, short-lived credentials from Vault or RDS IAM. AWS paths experimental.
